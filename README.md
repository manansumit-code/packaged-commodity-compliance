# Packaged Commodity Compliance Scanner — backend MVP

**SIH26034** — Software system to check compliance of packaged commodities under the
**Legal Metrology (Packaged Commodities) Rules, 2011**, by scanning product labels.

Backend only, on purpose. Scan a label image → get a machine-readable compliance
verdict. No frontend, because the question this build answers first is *how accurate
is the architecture*, and a UI cannot answer that.

not a pip package — install it first or nothing will run.

**1. Install Tesseract**

| Windows | installer from the [UB Mannheim builds](https://github.com/UB-Mannheim/tesseract/wiki), then add `C:\Program Files\Tesseract-OCR` to your PATH |

Check it worked: `tesseract --version` — it must print 5.x from a **new** terminal.

> but untested — if you are the first teammate on either, please correct this table in
> a PR once you have it working.

**2. Clone and create a virtual environment**

```bash
git clone https://github.com/manansumit-code/packaged-commodity-compliance.git
cd packaged-commodity-compliance
python3 -m venv .venv
```

Then activate it — this is the step that differs per OS, and every command in the

| Windows PowerShell | `.venv\Scripts\Activate.ps1` |
| Windows cmd.exe | `.venv\Scripts\activate.bat` |

Your prompt should now start with `(.venv)`. Re-activate it in every new terminal.

**3. Install dependencies and prove it works**

```bash
pip install -r backend/requirements.txt
python backend/verify.py          # expect: 11/11 checks passed
```

If `verify.py` reports 11/11, your environment is correct and everything below will
work. If it fails on Tesseract, step 1 did not take effect in this terminal.

> **Do not commit `.venv/`.** It is in `.gitignore` for a reason: a virtualenv hardcodes
> absolute paths from the machine that built it, so a committed one is broken for
> everyone else. Each person creates their own.

## The two hard problems, and what this build does about them

The problem statement looks like "OCR + a checklist". Two sub-problems inside it are
real engineering, and everything else is downstream of getting them right.

### 1. A photograph has no physical scale

Rule 7 is stated in **millimetres**. A camera image has no inherent millimetre. The
same pixel height is small print close up or large print far away, so no amount of
image processing recovers a physical size from a photo alone.

**Solution: a printed ArUco marker of known side length, coplanar with the label.**

- Four marker corners in the image plus four known corners in millimetre space give an
  exact planar homography — **no camera intrinsics, no focal length, no distance
  assumption**.
- The whole frame is then **rectified into that metric plane**, so tilt is corrected
  exactly (a homography is exact for a plane) and the rectified image has a constant,
  known px/mm.
- The homography is recomputed **every frame**. Bumping the camera cannot silently
  invalidate a calibration, which is the failure mode a one-time calibration has.

Verified: re-detecting the marker on the generated card recovers its scale to **+0.31 %**.

### 2. An OCR bounding box is not a numeral height

An OCR word box is a *detection* rectangle. It absorbs anti-aliasing halos, line
padding, the `₹`/`Rs.` prefix, and the decimal point — which is taller than a digit.
Measuring it measures the wrong thing.

**Solution: measure the ink, not the box.** Two stages ([`measure.py`](backend/lmpc/measure.py)):

1. **Segment** — binarise the field crop (Otsu, ink = minority class), take connected
   components, keep only numeral-shaped ones (aspect ratio, fill ratio, not touching
   the crop border, height-consistent with neighbours). OCR *character* boxes restrict
   this to columns the recogniser called a digit — that is how `₹` and `.` are dropped.
2. **Refine** — find each glyph's top and bottom edge as the **50 %-intensity crossing**
   of its vertical profile, to sub-pixel precision. Under a symmetric blur the 50 %
   crossing does not move, so this is far less biased than an integer binary extent at
   the ~10–20 px a 1 mm numeral actually occupies.

The reported height is the **median across glyphs**, never a single reading.

## Design decisions, and why

| Decision | Choice | Reason |
|---|---|---|
| Camera or upload? | **Both — one code path.** `scan_image(frame)` is frame-agnostic; the CLI feeds it webcam frames, the API feeds it uploads | The measurement problem is identical. Upload is what makes accuracy *reproducible*, which is the point of this build |
| OCR engine | **Tesseract 5, local** | Returns per-character boxes, which the measurement stage needs. Runs offline — nothing on the scanning path can fail on venue wifi |
| Field classification | **Regex / keyword rules** | Bounded vocabulary, microseconds per frame, offline, and **cannot invent a value that is not on the label**. Every value returned is verbatim OCR text |
| Legal thresholds | **Hardcoded tables, looked up deterministically** | No model of any size gets to produce a legal number. `GET /api/rules` discloses every threshold applied |
| Line grouping | **Rebuilt geometrically from word boxes** | Tesseract splits `"Month & Year of Manufacture: 09/2023"` into two "lines", destroying the key→value link. After rectification, printed lines really are horizontal |
| Verdict | **Three tiers, band fitted from data** | See below |

### Field classification is where the hours went

Three mechanisms, in order of how much they mattered:

1. **Geometric line reconstruction** — biggest single win. OCR line grouping is not
   printed-line grouping.
2. **Key-anchored windows** — a declaration wraps across lines
   (`"Manufactured by:"` / name / street / city–PIN). The key is anchored on one line
   and the value is sought across it and the next few geometrically-plausible ones.
3. **Negative keys** — a pack carries *other* dates and *other* prices. Best-before,
   expiry, batch codes, per-100 g and promotional prices are explicitly excluded, and
   when a positive and negative key share a line
   (`"Mfg. 03/2025  Best Before 09/2025"`) the search is truncated between them.

Plus: OCR-confusion tolerance on units (`"250 ¢"` → 250 g), applied **only** when a
`Net Qty.` key phrase anchored the match, so it cannot invent quantities.

## The verdict is three-tiered, and the band is measured

A raw pixel-to-millimetre reading carries real error. Reporting a confident **FAIL**
on a measurement that is within that error of the legal threshold is a false precision
claim — and in an enforcement context, a false accusation.

- **PASS** — measured height is above the requirement by more than the error band
- **BORDERLINE → manual verification** — inside the band
- **FAIL** — below the requirement by more than the band

The band is **not a guessed constant**. It is `max(|bias| + k·σ, p99|error|)`, fitted on
the calibration split — and specifically on the population the pipeline is actually
willing to adjudicate, so it describes the cases it is used on.

**k is 4, not the conventional 2, and that was forced by evidence.** A band built from
k=2 came out at ±0.083 mm and, on the held-out validation set, produced a **false
violation**: an MRP genuinely 1.125 mm tall (compliant) was measured at 0.870 mm and
called FAIL. [`band_sweep.py`](backend/eval/band_sweep.py) replays every validation
measurement across a range of bands and shows the whole trade-off:

| band | decisive | wrong decisive |
|---|---|---|
| 0.05 mm | 95.5 % | 2 |
| 0.083 mm *(k=2)* | 91.7 % | 1 |
| 0.15 mm | 86.5 % | **0** |
| 0.156 mm *(k=4, shipped)* | 86.3 % | **0** |
| 0.30 mm | 74.5 % | 0 |

Giving up ~5 % of decisive answers to remove the last false accusation is the right
trade for a tool whose output is a legal verdict. **Disclosed:** k was raised after
seeing that sweep, so the final validation figures are not blind to that one choice.
The sweep is shipped so the threshold can be re-chosen on your own data.

**The fitted bias is never silently subtracted from a measurement.** De-biasing a legal
verdict is an adjustment that has to be visible; the bias is accounted for
conservatively through the *width* of the band instead. (`apply_bias_correction` exists,
defaults off, and is reported when on.)

### Mis-measurement and mis-identification are different failures, kept apart

The first version of this build fitted the band on *every* measurement, including ones
where the extractor had located the **wrong text** — a best-before date measured against
the manufacture-date requirement. That inflated σ twentyfold and produced a band of
**±1.0 mm against a 1 mm threshold**: the system abstained on 39 % of cases and was
decisive on 28 %. A band wide enough to absorb a misclassification is not a measurement
band, and it destroys both numbers.

They are now separated:

- The **band** describes measurement error on a *correctly identified* numeral.
- **Misidentification** is reported separately (the precision column in §1 of the
  accuracy report) and is *gated*, not absorbed: a declaration matched only by a bare
  value pattern — a currency amount with no "MRP" near it, a date with no "Mfg." near it
  — has its height **reported but not adjudicated**
  (`MIN_MATCH_CONF_FOR_VERDICT`). The threshold belongs to a declaration we are not
  certain we are looking at.

The accuracy report then **checks the band against the population that actually receives
a verdict** (`3b_band_validation_on_adjudicated_population`), because that set is not the
same as the set the band was fitted on.

## What the system refuses to answer

A compliance tool that always returns a number is worse than one that knows when it
cannot. Five gates produce "not assessed" instead of a verdict:

| Gate | Fires when | Why it matters |
|---|---|---|
| `NO_REFERENCE_MARKER` | nothing in frame establishes scale | no marker, no millimetres — presence checking still runs |
| `EXCESSIVE_TILT` | marker too oblique | a conservative operator guideline, **not** derived from the sweep — the error data shows no clean growth through 30°. Note the side-ratio proxy over-reads true tilt (~24° reported for ~18° actual), so it binds tighter than its number suggests |
| `INSUFFICIENT_RESOLUTION` | numeral imaged below the fitted px/mm floor | below it, error is a third of a millimetre against a 1 mm threshold |
| `PANEL_NOT_COPLANAR` | rectified text baselines are not flat | a weak indicator only — see below |
| `LOW_LEGIBILITY` | OCR confidence / text size too low | a declaration OCR could not read is **not** a declaration that is absent. Reporting the first as the second is a false accusation, so absence becomes NOT ASSESSED |
| `GLYPH_COUNT_MISMATCH` | segmentation found a different number of numerals than the recogniser read | see below — this single check contains essentially the whole error tail |
| low field-match confidence | declaration identified only by a bare value pattern | the threshold belongs to a declaration we are not sure we are looking at |

### The two stages have to agree with each other

The measurement stage segments glyphs; the OCR stage reads characters. If OCR read
`02/2026` (six numerals) and segmentation kept four, the two disagree about what is
physically on the label — glyphs have merged, or been dropped, and the median is being
taken over the wrong set.

Measured on the calibration split, this one check separates the error distribution
almost cleanly:

| | share | σ | p95 \|e\| | worst case |
|---|---|---|---|---|
| counts agree | 86 % | **0.037 mm** | 0.089 mm | **0.198 mm** |
| counts disagree | 14 % | 0.241 mm | 0.635 mm | 1.084 mm |

So the 14 % that disagree contain effectively every large error. Their height is still
**reported** — it is just not **adjudicated**. That is a 14 % cost in yield to remove the
entire tail, which is the right trade for a tool whose output is a legal verdict.

### Coplanarity is an operator requirement, not something the system can verify

If the marker card and the declaration panel are on **different planes** — a card lying
flat on the table beside a standing carton — the marker can look perfectly square-on
while every millimetre reading is wrong. This is the one silent-wrong-answer mode the
three-tier design does *not* eliminate.

A negative control ([`test_coplanarity.py`](backend/eval/test_coplanarity.py)) renders
the marker and panel on deliberately different planes and measures the cost:

| plane mismatch | measurement error | baseline-slope statistic |
|---|---|---|
| 0° (control) | −0.006 mm | 0.01° |
| 5° | +0.035 mm | 0.05° |
| 10° | +0.077 mm | 0.18° |
| 20° | +0.173 mm | 0.60° |
| 30° | +0.264 mm | 0.74° |

**A 10° mismatch already exceeds the measurement error band.** The baseline-slope
statistic tracks the fault monotonically, but its spread on *genuinely coplanar* frames
overlaps that range, so it is reported as a weak indicator and **does not reliably fire**.
Lay the card flat against the same face as the printing; that is the control that works.

## Measured accuracy

340 held-out validation images, disjoint from the 220 used to fit the band and gates.
Full detail in [`backend/data/ACCURACY.md`](backend/data/ACCURACY.md); regenerate with
`eval/run_eval.py`.

> These numbers describe **synthetic labels through a simulated imaging chain**. They
> measure the architecture, not real retail packaging. Real print adds halftoning, dot
> gain, gloss, colour, reversed text and lens distortion, none of which is modelled —
> expect lower recall and a larger σ on real packs, and refit the band with
> `calibrate-physical` before trusting any threshold.

### The verdict the user actually sees

| | value |
|---|---|
| Packs decided (not sent to review) | 56.8 % |
| **Accuracy when decided** | **92.7 %** |
| **Violating pack wrongly CLEARED** | **0 / 340 (0.0 %)** |
| Compliant pack wrongly ACCUSED | 14 / 340 (4.1 %) |

Every wrong verdict is a false *accusation*, never a false clearance, and all 14 come
from OCR **missing** a declaration that was printed — not from mis-measurement. That is
the recall column below, and it is where remaining work belongs.

### 1. Field extraction (legible frames)

| declaration | recall | precision | value exact |
|---|---|---|---|
| commodity_name | 1.000 | 1.000 | — |
| mfg_date | 0.989 | 0.968 | 0.952 |
| consumer_care | 0.978 | 1.000 | — |
| manufacturer | 0.966 | 1.000 | — |
| mrp | 0.933 | 1.000 | 0.888 |
| net_quantity | 0.908 | 1.000 | 0.901 |

82.7 % of frames were judged legible enough to assert a declaration is absent; on the
rest, absence is reported as NOT ASSESSED rather than as a violation.

### 2. Height estimation

Conditioned on the extractor having read the right text — i.e. isolating the measurement
stage: **bias +0.0016 mm, σ 0.129 mm, MAE 0.033 mm, p95 |error| 0.110 mm** (n = 758).
Yield: 93.2 % of located declarations produced a height, 80.4 % end-to-end.

| capture resolution | MAE |
|---|---|
| 6–9 px/mm | 0.134 mm |
| 9–12 px/mm | 0.050 mm |
| 12–16 px/mm | 0.040 mm |
| 16–22 px/mm | 0.030 mm |
| ≥22 px/mm | 0.025 mm |

### 3. Legal verdict, per field

| field | decisive | accuracy on decisive | false CLEAR | false VIOLATION |
|---|---|---|---|---|
| net_quantity | 67.2 % | 1.000 | 0 | 0 |
| mrp | 67.3 % | 1.000 | 0 | 0 |
| mfg_date | 79.1 % | 1.000 | 0 | 0 |

Near the threshold (within 0.3 mm) the system answers BORDERLINE 47 % / 32 % / 0 % of
the time and makes **no wrong decisive calls**. Clear of the threshold, accuracy is
1.000.

**"Zero" is a bound, not a guarantee.** Zero errors in 667 adjudicated measurements
bounds the rate at roughly **0.5 %** (rule of three), on the split that informed the
choice of k — not at zero.

The band was independently checked against the population that actually receives a
verdict: p95 |error| 0.087 mm, p99 0.159 mm, against a ±0.156 mm band — 1.05 % fall
outside it.

### Performance

Measured on a 2844×2213 frame, single process, nothing else running:

| mode | latency |
|---|---|
| full (2 page-segmentation modes) | 4230 ms |
| `fast=true` (1 mode) | 2085 ms |
| `fast` at 1080p | 1933 ms |
| **calibration + rectification alone** | **77 ms** |

The geometry — the part that makes physical measurement possible — is real-time. OCR is
the entire cost. The live camera view therefore refreshes at roughly **0.5 fps behind a
smooth video feed**, not per-frame; it is a live *viewfinder with periodic assessment*,
not real-time analysis. Treat that as the honest claim.

## Scope

**In scope:** flat / near-flat **printed** packaging (cartons, boxes, pouches, flat
labels); Latin-script declarations (Devanagari if the Hindi pack is installed).

**Out of scope, stated rather than faked:**

- **Curved surfaces** (bottles, jars, cans) — the label is not coplanar with the marker,
  so the metric homography is invalid for it.
- **Embossed / debossed text** — needs raking light to be visible to OCR at all. The
  embossed column of the rule table is implemented; embossing *detection* is not.
- **The common/generic name** — not separable from brand text by rule. Reported as
  *excluded by rule*, never as a violation.
- **Rule 7 Table II** (length / area / number declarations) — keyed on principal display
  panel area, which cannot be measured from a photo of one face. Supply
  `panel_area_cm2`, or the system returns "requires panel area".
- **The MRP threshold attachment is a live legal question.** Table I is indexed by net
  quantity and is applied to the net-quantity numerals. Whether the same height binds
  MRP numerals, or whether MRP falls under the Rule 7(3) 1 mm floor, is **not settled by
  the source document**. The conservative reading is binding; the stricter reading is
  reported as **advisory**. It is one row in [`rules.py`](backend/lmpc/rules.py) to change.

## Before any real use: physical calibration

The shipped band is fitted on **synthetic** captures. The build plan requires it be
fitted on ruler-measured samples through the real camera. The harness ships:

```bash
open backend/assets/height_calibration_sheet_A4_600dpi.pdf   # print at 100%
# photograph it at several distances and angles, with the marker in frame
python backend/lmpc/cli.py calibrate-physical ./photos --marker-mm 40.0
```

Rows print numerals at 1.0–6.0 mm; the *true* height of each row comes from the font's
outline metrics (validated against a 400 px raster: agreement to 0 px across four
fonts). The command writes a real `uncertainty.json` whose `source` says "PHYSICAL".

## Layout

```
backend/lmpc/
  rules.py         Rule 6 + Rule 7 tables, quantity parsing, three-tier verdict
  calibration.py   ArUco detection, metric homography, rectification, px/mm
  ocr.py           Tesseract, geometric line reconstruction, content cropping
  measure.py       glyph segmentation + sub-pixel ink-height measurement
  fields.py        key-anchored windows, negative keys, value extraction
  pipeline.py      orchestration + the five refusal gates
  report.py        human-readable report      db.py  SQLite history
  api.py           FastAPI                    cli.py command line
backend/eval/
  synth.py             label generator + independent ground truth + imaging chain
  run_eval.py          three-accuracy evaluation, gate derivation
  demo_cases.py        the PASS / FAIL / BORDERLINE three-way demo
  test_coplanarity.py  negative control for the coplanarity gate
backend/assets/  printable calibration card, known-height sheet, marker
backend/verify.py    one-command end-to-end self check (11 checks)
```

## Reproducing the accuracy numbers

```bash
python backend/eval/run_eval.py --n-calib 220 --n-valid 340 --workers 6
python backend/eval/summarize.py     # -> backend/data/ACCURACY.md
python backend/eval/band_sweep.py    # the band trade-off curve
```

The calibration split fits the band and the gates; the validation split is disjoint and
reports against them. `--report-only` and `--derive-only` rebuild the report or the gates
from saved records without re-scanning.

## Working on this

**Before you push, run these three.** They are fast and they catch most breakage:

```bash
python backend/verify.py               # 11 end-to-end checks — must be 11/11
python backend/eval/test_rules.py      # rule table + field extraction unit tests
python backend/eval/test_coplanarity.py  # negative control for the coplanarity gate
```

They are plain scripts, not pytest — run them directly and check the exit code.

`verify.py` regenerates `backend/data/demo/*.jpg`, and the synthetic imaging chain is
not byte-deterministic, so `git status` will show those three as modified afterwards.
That is expected. Discard them rather than committing the churn:

```bash
git checkout -- backend/data/demo/
```

**Where a change belongs**

| Changing… | goes in |
|---|---|
| a legal threshold or rule row | [`rules.py`](backend/lmpc/rules.py) — the tables are data, not logic |
| how a declaration is found on the label | [`fields.py`](backend/lmpc/fields.py) — key phrases, negative keys, value patterns |
| what the system refuses to answer | [`pipeline.py`](backend/lmpc/pipeline.py) — the refusal gates live together on purpose |
| the numeral measurement itself | [`measure.py`](backend/lmpc/measure.py) — read §2 above first |
| a new API endpoint | [`api.py`](backend/lmpc/api.py); the matching CLI verb goes in [`cli.py`](backend/lmpc/cli.py) |

**Three things that will bite you**

1. **Never commit `.venv/` or `backend/data/scans.db`.** Both are per-machine and both
   are already in `.gitignore`. A committed venv hardcodes absolute paths and breaks
   for everyone else.
2. **`backend/data/uncertainty.json` is fitted output, not config.** It holds the error
   band. Regenerate it with `run_eval.py` or `calibrate-physical` — editing it by hand
   invalidates every accuracy claim in this README.
3. **If you change `rules.py`, `fields.py`, `measure.py` or `pipeline.py`, the accuracy
   numbers above are stale.** Re-run the evaluation and regenerate `ACCURACY.md`, or say
   in your PR that you did not.

**Workflow** — branch off `main`, keep the three checks green, open a PR. If a change
moves an accuracy number, put the before/after in the PR description; those figures are
the point of this build.
